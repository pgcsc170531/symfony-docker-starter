# Defect log and post-playwright backlog

One table for everything that is wrong, one table for everything we want changed.
Both live here so that a walkthrough leaves a paper trail instead of a pile of
invisible fixes.

## How to write an entry

| Field | Rule |
|---|---|
| **ID** | `P-<role>-<n>`, e.g. `P-BURSAR-03` |
| **Severity** | **Blocker** (the role cannot finish) · **Major** (wrong outcome or money) · **Minor** (cosmetic / wording) · **Data** (a record came out wrong) |
| **Where** | The full URL, and the tenant it was on (`demo.localhost:8082/...`) |
| **Did / Saw / Expected** | Three lines. "I clicked Confirm Payment" / "balance stayed ₦67,000" / "balance should drop to ₦0" |
| **Evidence** | Screenshot name, network status, or the console line |
| **Reproduce** | Numbered steps if it took more than one action |

Do not write "broken" without the three lines — a defect nobody can reproduce gets
re-discovered as a "known issue" three months later.

### Observations (not defects)

- `POST /admin/school/new` with an empty form is stopped by **HTML5 `required`** before it reaches the server (`school[name]`, `[subdomain]`, `[principalName]`, `[principalEmail]`, `[principalPassword]`). No record is created, which is correct; flagged in backlog so we decide whether server-side messages should also be visible to a non-JS client.
- **The tenant login on the bare domain is a 500, not a sentence.** `POST /login` on `localhost:8082` (the host the marketing page is served from) hits the tenant firewall, which authenticates against the *tenant* connection — and `.env` still points the default `DATABASE_URL` at the dummy `school_a`, a database that was dropped with the old tenants on 21 Oct. Result: `SQLSTATE[HY000] [1049] Unknown database 'school_a'`. Super admins belong on `/admin/login`, so this only misfires when someone uses the public "Staff portal" link. Decide between (a) pointing that link at `/admin/login`, (b) refusing a tenant login on the base domain with a sentence, or (c) keeping a real `school_a` around for local work.

## Why the split

A defect says *the system does not do what it already promises*. A backlog item says
*we want it to promise something else*.

**Defects are fixed during the walkthrough** — that is why the walkthrough exists. The
fix is made, the step is re-run from the start of that step, and the entry is closed with
the re-run as evidence. **Backlog items wait**: they are product decisions, and building
them mid-run changes the thing under test.

## Severity in practice, for this product

- **Blocker** — a role cannot complete its core job: a parent cannot see fees, a
  teacher cannot submit a score, a bursar cannot confirm a transfer.
- **Major** — the job completes but a figure, a document or a permission is wrong: a
  statement total disagrees with the debtors list, a report card shows another pupil's
  marks, a parent can open a sibling's invoice they should not see.
- **Minor** — the job completes correctly and looks wrong: a label reads "Recieve", a
  badge is misaligned at 320px.
- **Data** — the job completes but the stored record is wrong: a pupil lands in the
  wrong class after an import, a discount is applied twice.

## Closing an entry

Only close a defect with both:

1. The fix committed (cite the commit or the file), and
2. The **same step re-run** in the same role playbook, with the new result noted.
   "Fixed" without a re-run is a guess.
